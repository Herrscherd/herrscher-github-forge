# herrscher-github-forge

The GitHub forge plugin of [herrscher](https://github.com/Herrscherd/herrscher). It implements the `Forge` port of [herrscher-contracts](https://github.com/Herrscherd/herrscher-contracts) for GitHub.com and GitHub Enterprise Server.

The plugin registers itself under the kind `github`, in the category `forge`. The host builds one forge per forge host from the registered factory. The plugin calls the REST and GraphQL APIs directly.

## What it does

- Connection: who the token belongs to, where the token came from, its scopes and the rate limit left.
- Repository access: the permission the account holds on one repository.
- Repositories: the repositories the account can read (owned, collaborated on, or through an organization membership), listed a page at a time by name. A repository is left out of the page, without failing it, in three cases: its owner or name is refused by `ParseRepoRef`, its default branch name is refused by `ParseBranchName`, or `NewForgeRepo` refuses it, which happens when its clone URL is not an https URL of that repository on the forge host (a clone URL naming another repository, or served from another host). The contracts port asks for this skip, and the plugin does not report it: one bad repository must not fail the other repositories of the page, and the plugin has no logger to report a skipped one. A page can be empty while `Next` is not. When every repository of a page is skipped, the page comes back with no items and the `Next` the forge gave; the plugin does not request further pages to fill it, so the caller follows `Next` until it is empty.
- Pull requests: open, read, and merge with a chosen method. A read returns a revision, an opaque composite of the validators of the pull request and of every listing the read covers (see Revisions below). Passed back as `since`, it lets an unchanged pull request cost only conditional requests that answer 304, and the read returns `ErrForgeNotModified` when all of them do. `OpenPullRequest` returns no revision, so the first read after opening is a full read.
- Checks: the check runs and commit statuses of a commit, paged. On the pull request path, the checks come from the REST check runs (`filter=latest`) and the combined commit status, which accept `If-None-Match`, not from the GraphQL rollup. A check run or status that the forge refuses (403, or 404 for a missing permission) does not fail the pull request: it is returned with `ChecksUnknown`. Any other failure is returned as an error. `Checks` reads the same two listings through the same mapping: the check runs first, then the statuses, cut into pages by an offset cursor. Each call reads both listings in full (up to 20 pages each) and returns the requested slice, and a refused listing is an error rather than unknown checks. The offset cursor counts into the merged list of both listings, so a check added or removed between two calls shifts the offsets: a check can then come back twice or be skipped. A listing over 20 pages fails the call with an error wrapping the plugin's page limit, with no checks returned. This failure is untyped: no contract sentinel names it, so the error is returned as is and a caller cannot match it. `Checks` is called by an explicit command, and the pull request path does not use it: `PullRequest` degrades this failure instead. A check run that comes from GitHub Actions carries the identifier of its job, whose log can be read. Each check carries the identifier of the app that produced it (`AppID`, taken from the check run's app, 0 for a commit status) and its `Attempt`: the identifier GitHub gives the check run, or the identifier of the commit status. GitHub does not document that these identifiers grow with each re-run, so `Attempt` is an identifier to compare for equality, not an ordering to rely on. A check run status, a status context state or a check kind the plugin does not know fails the read of the checks with an error that quotes the value, and no checks are returned. A check is never reported as waiting or finished by default, so a caller waiting for completion cannot loop on a state the plugin never mapped.
- Required checks (`RequiredChecks`, the optional `contracts.RequiredChecksSource`): the checks a branch requires before it can merge. They come from two sources, read in this order: the repository rulesets that target the branch (`rules/branches/<branch>`, paged, up to 20 pages), then the classic branch protection (`branches/<branch>/protection/required_status_checks`). A ruleset requirement carries the `integration_id` of its app and a classic requirement carries its `app_id`, with 0 for a context that any app may satisfy. Both sources are merged and deduplicated by name and app, so the same check named in both comes back once. A classic protection that answers 404 means the branch has no classic protection: it contributes no requirement, and the rulesets still count. A branch that requires nothing returns an empty list. The read fails with `ErrRequiredChecksUnknown` when the rulesets or the protection are refused or fail, and when a requirement has no name. The call refuses a zero branch name with an error before any request is sent.
- Job logs: the tail of a CI job log, up to 1 MiB.
- Review threads: the threads of a pull request, and replies to them.
- Issues: one issue, and a filtered listing of issues (pull requests are left out of the listing and refused by number).
- Pull request event feed (`PullRequestEvents`, the optional `contracts.PullRequestFeed`): one stream of changes of one pull request, read from the event subscriptions preview API that `gh event listen` uses. The plugin creates a subscription for the five pull request event types, then reads its `text/event-stream`. Each event maps to one kind of `PullRequestEventKind`: review submitted, new commit (head changed), state changed, merge conflict, checks changed. An event of another type is ignored. The feed is live only: the forge sends no replay, so a signal does not cover a change made while the stream was down, and the caller reads `PullRequest` to see the current state. A stream that stops sending heartbeats for about 27 s (three heartbeats of 9 s) ends with `ErrFeedSilent`. The plugin times the response headers itself, 30 s from the request: when they do not arrive in time, `PullRequestEvents` returns `ErrFeedSilent` at open, with no channel. A stream the forge ends with `reconnect`, or with a subscription end such as `expired`, ends with `ErrFeedEnded`: the host re-subscribes with a growing delay and runs a catch-up read of `PullRequest`, because the feed carries no replay. A subscription lasts 24 h, so a feed that runs that long ends with `ErrFeedEnded` at that point. A stream the forge ends as access revoked ends with `ErrFeedRefused`. Each of these is the last signal, and the channel closes after it. An event whose data is not valid JSON is ignored, without a log, and the stream continues. The pump sends no new signal once it has observed the cancellation. A signal may still be received if the cancellation lands between the pump's context check and its choice between the send and the cancellation. A caller treats the channel closing, not the last signal, as the end of the feed.

## Endpoints

| Host | REST | GraphQL |
|---|---|---|
| `github.com` | `https://api.github.com` | `https://api.github.com/graphql` |
| any other host (GitHub Enterprise Server) | `https://<host>/api/v3` | `https://<host>/api/graphql` |

## Credentials

The plugin never reads a token from the environment, from a file, or from the `gh` command line. For each request it asks the host's `ForgeCredentials` for the token of its forge host and sends it as `Authorization: Bearer`. When GitHub answers 401, the plugin calls `Invalidate` so the host drops the token it cached.
Every request also sends `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28`.

## Errors

Failures wrap the sentinels and error types of the contracts port:

| Answer | Error |
|---|---|
| no credential for the host | `ErrForgeNotConnected` |
| 401 | `ErrForgeUnauthorized` (and `Invalidate` is called) |
| 403 without a throttle signal | `ErrForgeForbidden` |
| 403 with `x-ratelimit-remaining: 0` or `Retry-After`, or 429 | `ForgeRateLimitedError` |
| 404, or a GraphQL `NOT_FOUND` | `ErrForgeNotFound` |
| 304 on every request of a pull request read with a revision (the pull request and each listing the revision covers) | `ErrForgeNotModified` |
| 403 or 404 with the message `Event subscriptions are not enabled for this account` on the event feed (preview not granted to the account) | `ErrFeedRefused` at open, and no channel |
| a repository on a GitHub Enterprise Server host, for the event feed | `ErrFeedRefused`, with no request sent (the feed exists on GitHub.com only) |
| an event feed stream ended as `access_revoked` | `ErrFeedRefused`, as the last signal of the feed |
| an event feed stream ended as `reconnect` or as a subscription end (`expired`, `deleted`) | `ErrFeedEnded`, as the last signal of the feed; the caller re-subscribes and reads `PullRequest` to catch up |
| no response headers on the event feed within 30 s, timed by the plugin | `ErrFeedSilent`, returned by `PullRequestEvents` with no channel |
| a dial, TLS handshake or other connection failure on the event feed, including its timeout | the plain error, not `ErrFeedSilent`, returned by `PullRequestEvents` with no channel |
| 403 or 404 on the check runs or the commit statuses of a pull request | the pull request is returned with `ChecksUnknown` and no error |
| 403 or 404 on the reviews of a pull request | the pull request is returned with an empty `LatestReview` and no error |
| 403 on the check runs or the commit statuses of `Checks` | `ErrForgeForbidden`, with no checks returned |
| 403 on the rulesets or on the classic protection of a branch, in `RequiredChecks` | `ErrRequiredChecksUnknown`, wrapping `ErrForgeForbidden` |
| 404 on the rulesets of a branch, in `RequiredChecks` | `ErrRequiredChecksUnknown`, wrapping `ErrForgeNotFound` |
| 404 on the classic protection of a branch, in `RequiredChecks` | no classic requirement, and no error: GitHub answers 404 for a branch without classic protection |
| a requirement with an empty name, in `RequiredChecks` | `ErrRequiredChecksUnknown`, wrapping `ErrEmptyRequiredCheckName` |
| a listing of more than 20 pages read by `Checks` | an untyped error wrapping the page limit, returned as is, with no checks returned; no contract sentinel names it, so a caller cannot match it |
| a revision that is empty, malformed or of another version | read in full, with no conditional header |
| merge refused with 405 or 409 | `ForgeMergeRefusedError`, with the merge state read back from the forge |
| `Issue` called with the number of a pull request | `ErrNamesPullRequest`, which also matches `ErrForgeNotFound` |
| issue listing with a label that holds a comma | `ErrInvalidLabel`, and no request is sent |

A repository on another host is refused with `ErrForgeWrongHost`, and a namespace of more than one segment with `ErrInvalidRepoRef`.

## Limits and quota

- Response bodies are read up to 8 MiB. A larger body is refused.
- At most 4 requests are in flight at once. A caller waiting for a slot stops when its context is done.
- Only REST core responses update the quota the plugin holds for the token (`x-ratelimit-limit`, `-remaining`, `-reset`, when `x-ratelimit-resource` is `core` or absent). A GraphQL response carries its own budget and is ignored for the quota, and GraphQL calls are not refused by the REST budget. Each REST core response that is not a 304 costs one request of that budget, and a 304 costs none. The quota is only taken from a response that carries both the limit and the remaining count. When the remaining budget is below 10% of the limit and the reset is still ahead, further calls are refused with `ForgeRateLimitedError` without being sent. A response with `x-ratelimit-remaining: 0` and no reset header does not refuse calls locally: the forge did not say when the budget refills, so the call is sent and the answer is taken as usual.
- The event feed is governed by the same REST core budget as the other REST calls, as the plugin assumes: its subscription POST and its stream open are refused locally when the budget is spent, and their responses update the quota. The event API's own accounting is not documented, so this is an assumption to confirm against real responses. The stream itself costs one request when it opens and is not re-opened by the plugin, so a long stream does not consume the budget.
- The event feed reads each event line up to 64 KiB and each event up to 256 KiB. A larger event ends the feed with an error rather than buffering without bound.
- Responses that arrive out of order cannot roll the quota back. Within one reset window the lowest remaining count is kept. A window that resets later replaces the earlier one, and a response of an earlier window is ignored.
- The rate limit a connection reports is the zero `ForgeRateLimit` (`Remaining` 0, `Reset` the zero time) when the response carries no `x-ratelimit-remaining` header: the forge did not say, as the contract documents for a missing reset.
- A throttle `Retry-After` is read as a number of seconds or as an HTTP date.
- Job logs: the plugin keeps only the last bytes asked for. If the log is larger than 256 MiB it refuses with an error rather than returning a partial tail.
- Redirects: the plugin follows at most 10 redirects. The `Authorization` header is removed when a redirect changes the scheme, the host or the port of the origin it was sent to, so a job log served from storage on another host, or from a plain HTTP address, never receives the token.
- Timeouts: the TLS handshake may take 10 s, the response headers 30 s, and an idle connection is kept 90 s. There is no timeout on the whole request, so a job log can stream.
- Revisions: the revision of a pull request is `v2;pr=…;head=…;checks=…;status=…;reviews=…`, where `pr` is the ETag of the pull request, `head` its head commit, and each listing holds the ETag of its first page, its page count from `Link` `rel="last"`, and whether its first page held 100 items, the page size the plugin asks for. A revision that does not parse as this version is treated as absent, so a `v1` revision written before this version is read in full once. A listing is never read partly: on the pull request path, a listing that spans more than 20 pages degrades like a refused one, and `Checks` returns an error for it. On a 304 of the pull request, the plugin probes the check runs, the commit statuses and the reviews of the revision's head with their validators, and re-reads the pull request in full when any of them changed; a head that changed invalidates the validators of the old head because the pull request itself then answers 200. The plugin assumes that GitHub honors `per_page`: every page but the last holds exactly the page size asked for, so a first page of 100 items is full and is always re-read, since its next page may hold a new item. A one-page listing whose first page is not full is probed with a 304 and its `Link` header is not read, since a 304 says only that the first page is unchanged. A listing that the revision records as spanning more than one page, or whose first page was full, is never probed: the read is full, so a change on a middle page, or a review added after a full first page, is always seen. A dismissed review still counts, because its id does not change.
- Request cost of a read with a revision. A pull request that answers 200 is read in full with no probe. A pull request that answers 304 is followed by one probe per listing, in the order check runs, statuses, reviews, and the probes stop at the first listing that is not probed (more than one page, or a full first page) or that answers 200. When every listing is probed and answers 304, the read costs the probes only: with nothing changed and every listing on one page of fewer than 100 items, that is 4 requests, all 304, which cost no quota. Otherwise the read is full: the pull request once more, then every page of the three listings. With k the probes sent, and P, S and R the page counts of the check runs, the statuses and the reviews, a read whose pull request answers 304 and that ends in a full read sends 2 + P + S + R + k requests. A 304 costs no quota, and each probe that does not answer 304 costs one unit: a probe that answers 200 (the listing changed), or 403 or 404 (refused), so the read costs 1 + P + S + R, plus one when the last probe did not answer 304 (the chain stops at the first such probe, so there is at most one). A list whose first page is full is therefore always read in full once the pull request answers 304, which keeps a listing that grows on a later page from being missed. Examples, both pinned by tests: 5 check runs at 2 per page (P = 3), 1 status (S = 1) and 1 review (R = 1) make 7 requests, 6 of which cost quota (`TestPullRequestCostWhenAListSpansPages`); 1 check run (one probe, 304), 5 statuses at 2 per page (S = 3) and 1 review (R = 1) make 8 requests, 6 of which cost quota (`TestPullRequestCostWhenAProbeChainStopsAtAMultiPageListing`). A probe answering 200 adds one unit (`TestPullRequestCostCountsAProbeThatAnswers200`: 6 requests, 5 of which cost quota), and so does a refused probe (`TestPullRequestCostCountsAProbeRefusedWithoutAnswer304`, for 403 and 404: 6 requests, 5 of which cost quota).
- Listings take a page of at most 100 items (default 30). A larger limit is refused with `ErrInvalidPageLimit`.
- A page cursor must be a page number of at least 1, and an empty or malformed cursor is refused before any request is sent. A `Link` header whose `next` target does not carry such a page number fails the page that carries it, with an error that quotes the value, instead of handing the bad cursor to the next call.
- Review threads: each thread returns all its comments, read 100 per request. A thread with more than 20 pages of comments is refused with an error rather than returned partly. A thread deleted while its later comment pages are read is left out of the listing. A later comment page that answers with a node which is not a review thread is refused with an error instead, since only an absent node counts as deleted.

## Development

The quality chain is `scripts/check.sh`: tidy, the golangci-lint set, the comment check (`tools/commentcheck`), the dash check, the tests with `-race`, the build with `CGO_ENABLED=0`, and `govulncheck`. CI runs the same script.

Tests run against `httptest` servers only. No test reaches the real GitHub.

The required checks are read from the ruleset and protection endpoints as their documentation describes them. Their answers, the meaning of `integration_id` and `app_id` as the app identifier of a check run, and the `Attempt` identifiers have not been checked against a live repository.

The event feed is a preview API. The protocol follows the `gh` CLI source (`pkg/cmd/event/client/client.go`, `pkg/cmd/event/listen/listen.go`, `internal/eventstream/sse.go` of cli/cli v2.105.0) and has not been checked against a live account that holds the preview.
